# 1.0 stabilization — the decision list

ROADMAP's Next section holds one item: settle the wire format and API surface, then commit to semver stability. A
full audit of the HTTP surface (160 routes), the reporter↔server wire contract, the 40-tool MCP registry and the CLI
produced two kinds of findings: inconsistencies cheap to fix immediately (shipped in #398/#400 — summarized at the
bottom), and **decisions** — places where 1.0 freezes whatever is chosen, so choosing has to happen first. This
document is the durable home for those decisions; the numbers below are stable references. When a decision ships,
move its entry to "Settled" with the PR number.

Every claim was verified against `main` after #398, #399 and #400 merged.

## Status

**Settled:** D1, D2, D3, D5, D6, D7, D8, D9, D10, D11, D14, D16 (details in the Settled section below).

**Remaining open — pick up here:** D4 (wire versioning + compat policy), D12 (reporter config surface),
D13 (CLI flag semantics), D15 (write informal contracts down), D17 (Test Map M3 contracts — documented as they
ship), D18 (Test Map M2 contracts), D19 (locator pages), D20 (steps files and `piwi codegen`), D21 (extension connect and URL patterns), D22 (bug reports), D23 (viewports in the locator index) and D24 (the suite in the editor). None of D4/D12/D13/D15 has been started. D4/D12/D13/D15 are largely
independent of each other, so any order works; each should ship as its own verified, separately-committed change
(typecheck + lint + unit + the relevant E2E) keeping the app green, and its entry moves to "Settled" when it lands.

Working convention used for the settled batch (carry it forward): **no backward-compatibility aliases** — clean
renames/breaks, moving the server route, demo router, UI/reporter consumers and E2E specs together in the same
change; wire fields (hand-built request/response JSON) are renamed while DB columns, Drizzle fields, internal
params and Vue prop names stay; the MCP registry is a separate wire surface with its own conventions.

## Open decisions

### D4. Wire versioning and the compatibility policy

There is no wire-format version anywhere in the reporter↔server exchange: `reporterVersion` is stored but never
branched on, unknown fields are silently ignored, missing fields silently default, and the reporter's only
compatibility mechanism is the any-error fallback ladder (streaming → upload → submit). Nothing pins reporter
*bytes* to server *handlers* — the drift test pins the declared types, which the ingest handlers do not use.
**Recommendation, as a package:** (a) write the policy down — "the server accepts payloads from any ≥1.0 reporter;
unknown fields are ignored" — in the OpenAPI description and `upgrading.md`, including which side to upgrade first;
(b) add a `wireVersion` field the server echoes and can someday reject with a distinguishable status; (c) have the
reporter preflight `GET /api/version` (unauthenticated, already exists) and log when a feature will degrade;
(d) add a golden-payload fixture test replaying canned 1.0 `submit`/`events`/`finish` bodies against the real ingest
routes, so "old reporters keep working" is CI-checked rather than hoped.

### D12. Reporter configuration surface

Env names diverge from option names in ways that freeze at 1.0: `inspectOnFailure` → `PIWI_INSPECT_ON_FAIL`,
`pickLocatorOnFailure` → `PIWI_PICK_LOCATOR_ON_FAIL`, `ai.mode` → `PIWI_AI`, `ai.maxSteps` →
`PIWI_AI_MAX_FLOW_STEPS`; `PIWI_AI_UPDATE` lives outside the `PIWI_ENV_KEYS` single-source map. The master switch
`collectPerformanceMetrics` has no env var while its three sub-toggles do. Docs drift: `reporter.md` claims every
option has an env var (false for ten), documents a `serverUrl` default that does not exist, and the npm README's
options table is roughly ten options behind with no drift test covering it. **Recommendation:** add the missing
env var and register `PIWI_AI_UPDATE`; either rename the divergent vars now with old names as aliases or bless them
in the docs as-is; regenerate the README table (or point it at the docs site) and fix the two false claims.

### D13. CLI flag semantics

`--project` means the Piwi project in `piwi init` but the *Playwright* project in `piwi ai resolve`; `--dir` means
the skills directory in `piwi skills add` but the AI-artifacts directory in `piwi ai check` while `init` calls the
former `--skills-dir`. Flag names are frozen contract for CI scripts at 1.0. Also `ci.md`'s table gloss of
`--require-tag` omits that a tag matching no test is itself a violation. **Recommendation:** rename
`ai resolve --project` → `--pw-project` (keeping the old flag as a hidden alias) and align `--dir` naming; fix the
doc gloss.

### D15. Write the informal contracts down

Not changes — documentation debts that become contract at 1.0: the multipart field-name mix (camelCase alongside
`trace_<i>`/`report_<type>`/`attach_meta_<i>`, plus the legacy `htmlReport` field still accepted); the `type:
'complete'` discriminant sent in batch payloads but undeclared in `TestCasePayload`; and the split time encoding
(run-level `startTime` ISO-8601 vs case/attempt/step `startedAt` epoch-ms) which is fine but stated nowhere.
**Recommendation:** declare all three in the wire types/OpenAPI as-is; drop `htmlReport` only if no external
producer used it.

### D18. Test Map external contracts (M2)

The Test Map (M2) adds three external contracts that freeze at 1.0: the **`piwi-page-inventory`** capture attachment
(`[{ url, controls: [{ role, name }], links: [{ name, href }] }]`, a `pageInventory` wire field on the per-case
payload); the **probe plan and results** exchange (`GET /probes/plan` → `{ budget, items: [{ testCaseId, testTitle,
routeKey, fault, nth }] }` and `POST /probes/results`), where the `fault` vocabulary (`status-500`, `empty-body`,
`drop-field`, `stale-value`, `slow`) is the frozen surface; and the **`X-Piwi-Probe`** request header the
instrumentation reads (base64 JSON `{ nonce, ts, specJson, sig }`, HMAC-SHA256 over `${nonce}.${ts}.${specJson}`),
shared by the Nitro and ASP.NET Core packages. **Recommendation:** declare the attachment and probe payloads in the
wire types/OpenAPI as-is; the probe header format is documented in each instrumentation README and versions with the
`v` field in the envelope if it ever changes.

### D17. Test Map external contracts (M3)

M3 adds more external contracts that freeze at 1.0, on top of the M2 ones in D18:

- The **declared-surface manifest** shape (`shared/types.ts` `AppManifest`): `{ routes: [{ method, pattern,
  handler?, responses? }], pages: [{ pattern, name? }] }`, uploaded through **`PUT /api/projects/:id/surface/manifest`**
  with body `{ source: 'instrumentation' | 'committed' | 'openapi', manifest: AppManifest }` and read through
  **`GET /api/projects/:id/surface/manifest`**. The committed file is **`piwi.manifest.json`** next to the Playwright
  config; the instrumentation packages serve the same route table (minus documented codes) at **`/__piwi/manifest`**
  (`{ routes: [{ method, pattern, handler? }] }`), fetched by the reporter's global setup only when the base URL's
  first response carries an instrumentation header.
- The **`X-Piwi-Probe` header at level two** (server probes): the same base64 `{ nonce, ts, specJson, sig }` envelope
  as D18, but `specJson`'s `fault` vocabulary widens to the server fault classes (`throw`, `status`, `delay`,
  `dependency`, `data`, `extreme`, `replay`, `auth`, `slow-first`), and the instrumentation answers with
  **`X-Piwi-Trace`** reporting the fault it actually applied so an un-honored probe is recorded as inconclusive.
- The **feature-graph endpoint** **`GET /api/projects/:id/graph`** (`?node=kind:key&depth=`, depth capped at six) and
  the `get_feature_graph` MCP tool: the neighborhood shape (nodes with their class, edges with their kind, and the
  tests on each hop) is the frozen surface.

**Recommendation:** declare the manifest shape and the surface/graph endpoints in the OpenAPI as-is; the manifest and
probe-header formats are versioned by the `v` field in their envelopes (probe) or an additive field (manifest) if they
ever change.

### D19. Locator pages

The page each locator call ran on ([`locator-stability-and-pages.md`](locator-stability-and-pages.md), Track B) adds
three external contracts that freeze at 1.0:

- The **`piwi-locator-pages`** capture attachment and the **`locatorPages`** per-case wire field:
  `[{ location, locator, origin, page, arrival }]` (`LocatorPageUse` in `@piwitests/core/wire`), where `location` is
  the call site as a step location reports it, `locator` the chain as `Locator.toString()` prints it, `page` the page
  key (`pageKey` in `@piwitests/core/page-key`: the path with ids and tokens collapsed, no query, no hash) and
  `arrival` whether no locator interaction ran on the page since its last navigation.
- The **page key normalization** itself: the extension computes the key of the page it is on with the same function,
  so a change to it has to reach the reporter, the server and the extension together.
- The locator index document's optional **`pages`**, and each use's **`pages`**, **`arrival`** and
  **`pagesTruncated`** (`GET /api/projects/:id/locator-index`), which the browser extension reads.

**Recommendation:** declare the attachment, the wire field and the index fields as they are; they are additive and
optional, so an older reporter, server or extension simply has no pages.

### D20. Steps files and `piwi codegen`

A recording as data ([`bug-report-to-failing-test.md`](bug-report-to-failing-test.md), Part 1) adds two external
contracts that freeze at 1.0:

- The **steps file** (`PiwiSteps` in `@piwitests/core/steps`, version `v: 1`): `{ v, title, origin, recordedAt, note,
  steps }`, each step `{ action, target, value, redacted, pageUrl, timestamp, assertion? }` with URLs on `origin`
  stored as paths, and the limits `parseSteps` enforces. Piwi Picker writes it (Download steps), `piwi codegen` reads
  it, and a tester's file must still read on a developer's newer tools. Documented in
  `apps/docs/reference/steps-format.md`.
- The **`piwi codegen`** command and its flags (`--out`, `--force`, `--body`, `--title`, `--test-import`,
  `--absolute-urls`, `--no-url-checks`, `--env-values`, `--fail`, `--fail-reason`, `--tag`, `--project`,
  `--server-url`, `--api-key`, `--offline`) and exit codes (0 written or printed, 2 unreadable steps or a failed
  write), part of D13's CLI surface.

The `hover` action joined `v: 1` before 1.0 shipped (Piwi Picker records the hover that reveals what a click lands
on); an older reader rejects a file holding one as an unknown action rather than misreading it, and no 1.0 reader
exists yet.

**Recommendation:** freeze `v: 1` as it is, with new fields added as optional ones and a new version only for a
change an older reader would misread; keep reading the pre-format recording shape (`{ steps, startedAt, startUrl }`)
through 1.0.

### D21. Extension connect and project URL patterns

Connecting Piwi Picker in one step and keeping its URL patterns on the instance
([`extension-connect.md`](extension-connect.md)) adds external contracts that freeze at 1.0, since a published
extension talks to instances of any later version:

- The **device-code endpoints**: `POST /api/extension/connect` (`{ browser?, os? }` →
  `{ deviceCode, userCode, verificationUrl, interval, expiresIn }`), `POST /api/extension/connect/token`
  (`{ deviceCode }` → `{ status }` with `pending`, `slow_down` + `interval`, `denied`, `expired`, or `approved` +
  `apiKey` + `user`), and the page `/extension/connect?code=` the extension opens.
- **`GET /api/extension/url-patterns`**: `{ user, items: [{ projectId, projectName, projectLabel, pattern,
  environment, branch }], projects: [{ id, label, canEdit }] }`, and `POST /api/projects/:id/url-patterns`
  (`{ pattern, environment?, branch? }`), which the extension calls.
- The **pattern syntax**: `urlMatches` in `@piwitests/core/function-match` (`*` within a path segment, `**` across,
  anchored at both ends).

**Recommendation:** freeze them as they ship. New fields are optional additions; a new `status` value would break an
older extension's polling loop, so the set stays closed.

### D22. Bug reports

Bug reports as failing tests ([`bug-report-to-failing-test.md`](bug-report-to-failing-test.md), Parts 3 and 4) add
external contracts that freeze at 1.0:

- The **`expectedStatus`** wire field on every test case (Playwright's `TestCase.expectedStatus`, one of `passed`,
  `failed`, `timedOut`, `skipped`, `interrupted`), and the outcome read from it: a row stored `failed` whose expected
  status is `failed` is an expected failure that passed. A payload without it is read from the `fail`, `skip` and
  `fixme` annotations.
- The **`piwi:bug`** annotation (a bug report id, digits, an optional leading `#`), beside `piwi:link`.
- The **`bug.looks_fixed`** notification event and its payload (`{ projectId, projectName, runId, branch?, tests:
  [{ title, filePath, executionId, testCaseId, bugId?, link? }] }`).
- The **endpoints** Piwi Picker and the CLI call: `POST /api/projects/:id/bug-reports` (multipart: a `report` part,
  the bug report `{ v: 1, steps, evidence, context }` read by `parseBugReport` in `@piwitests/core/bug-report`, an
  optional `language` part, up to three PNG `screenshot` parts named as `evidence.screenshots` names them; or a JSON
  body `{ report, language? }`; answers `201 { id, url }`), `GET /api/projects/:id/bug-reports` (`{ items }`, `status`
  filter), `GET /api/bug-reports/:id`, `PATCH /api/bug-reports/:id` (`{ title?, status? }`),
  `POST /api/bug-reports/:id/reproductions` (`{ verdict, source?, divergedAt?, origin?, userAgent?, runId? }`),
  `GET /api/bug-reports/:id/spec?mode=commit|run` (`{ code, fileName, path, warnings, mode }`) and
  `GET /api/bug-reports/:id/screenshots/:index`. The statuses (`open`, `test-committed`, `looks-fixed`, `closed`,
  `dismissed`) and verdicts (`reproduced`, `not-reproduced`, `diverged`) are a closed set an older extension reads.
- The **CLI**: `piwi bug <id>` (`--write`, `--out`, `--no-run`, `--force`, `--run-mode`, `--server-url`, `--api-key`;
  exit codes 0, 1 the run did not fail as `test.fail()` expects, 2) and `piwi codegen bug:<id>`, part of D13's surface.
- The **MCP tools** `list_bug_reports`, `get_bug_report` and `render_steps`.
- Filing in a tracker: the `createIssue` part of the send (`true`), its `issue` answer (`{ status, key?, url?, error? }`
  or null), `GET /api/projects/:id/bug-reports/intake` (`{ tracker, projectKey, locale, canCreate, fileEvery }`), and
  `bug_report` as an `entityType` of `POST /api/integrations/issues`, `GET /api/integrations/issue-draft`, the links
  endpoints and the MCP tool `create_issue`.
- Why the suite missed it: `GET /api/bug-reports/:id/missed-by` (`{ page, pagesKnown, visiting, targets, mainFile,
  summary, owner }`), the `missedBy` field of `get_bug_report`, and `escaped-defect` blind spots keyed `page:<pageKey>`.
- The **desktop repro request** Piwi Picker sends to the desktop app: `POST /api/desktop/repro-requests` (JSON only,
  415 otherwise; `{ steps, options?: { headed, trace, project, repeatEach }, title?, bugReportId?, instanceUrl? }`, the
  steps read by `parseSteps`; answers `201 { id, status, expiresAt, windowOpen }`), `GET /api/desktop/repro-requests/:id`
  (`status` one of `waiting`, `running`, `done`, `declined`, `expired`; `verdict` one of `reproduced { step, found }`,
  `not-reproduced`, `diverged { step, reason }`, `completed`, `stopped`), the shell command `desktop_run_repro`
  (`{ projectId, requestId, args }`, flags only) and the `PIWI_REPRO_RESULT` file the spec writes (`{ status, line,
  message }`).

**Recommendation:** freeze them as they ship; new payload fields are optional additions.

### D23. Viewports in the locator index

Open this page at a viewport ([`devtools-panel.md`](devtools-panel.md), 2.5) adds one external contract that freezes
at 1.0: the locator index document's optional **`viewports`**, `[{ project, width, height }]`
(`LocatorIndexViewport` in `@piwitests/core/locator-index`, `GET /api/projects/:id/locator-index`), which the browser
extension reads. It is read from the run metadata the reporter already sends (`htmlReport.projects[].use.viewport`,
with the project's `name`), so no reporter wire field is added; that metadata field becomes part of the contract too.

**Recommendation:** declare the field as it is; it is additive and optional, so an older server simply has no
viewports and the extension offers a size typed by hand.

### D24. The suite in the editor

Locator break prediction, code reach and the editor clients ([`suite-in-the-editor.md`](suite-in-the-editor.md)) add
external contracts that freeze at 1.0. Each PR of that plan adds its own here as it ships. The core functions
(`extractDiffAnchors`, `predictLocatorBreaks`, the text rules in `@piwitests/core/locator-text-match`) are private
to the monorepo and freeze nothing on their own; what freezes is what they produce on a wire or a command line.

- **`piwi preflight`** (part of D13's CLI surface): the flags `--base`, `--branch`, `--test-root`, `--locale`, `--fix`,
  `--run`, `--strict`, `--json`, `--server-url`, `--api-key`, `--project`, Playwright arguments after `--`, and the exit
  codes (0 ok, 1 a likely break left unfixed with `--strict` or `--run`'s tests failed, 2 no index and no cache, or no
  diff). The connection order: flags, environment, the workspace `.env`, the desktop discovery file.
- **The `--json` document** (`PreflightResult` in `packages/reporter/src/cli/preflight.ts`): `{ project, branch, base,
  index: { locators, tests, fromCache, truncated }, anchors, breaks, impact, edited }`, each break `{ anchor, locator,
  confidence, actions, tests, rewrite, sites }`, `anchor` being `DiffAnchor` (`file, line, oldLine, kind, attribute?,
  key?, before, after?`) and each site `{ callSite, action, edit?, holders? }` with `action` one of `edit`, `applied`,
  `by-hand`, `elsewhere`, `none`. Hooks and agents read it.
- **The MCP tool `predict_locator_breaks`** (`{ projectId, diff, branch? }` → `{ branch, locators, truncated, items,
  nextCursor }`, each item `{ locator, confidence, rewrite, change: { filePath, line, kind, attribute, key, before,
  after }, tests: [{ testCaseId, title, filePath }], callSites, edits: [{ before, after }] }`), part of the MCP registry.
- **Locator healing's `diff-rename` source** in `LocatorHealingSource`, with the result fields `fromDiffRename` and
  `diffRename: { before, after, file, line }`, served by `GET /api/test-run-cases/:id/locator-healing` and
  `get_locator_healing`. A client that switches on `source` must know the new value.
- **The pull-request comment section** "Locators this change breaks": its wording is not a contract, but its place
  (after Uncovered changes) and its rule (likely breaks whose tests did not run) are documented.
- **Code reach** (the reporter's `captureCodeReach` and `codeReachRoots` options, `PIWI_CAPTURE_CODE_REACH` and
  `PIWI_CODE_REACH_ROOTS`; `codeReachRoots` is tried before the repository root, which is always last): the **`piwi-code-reach`** attachment and the per-case **`codeReach`** wire field, a
  sorted `string[]` of repository-relative paths (at most 2,000); `GET /api/projects/:id/code-reach?file=&branch=`
  (`{ file, branch, tests }`, each test as in the locator index plus `origin`: `client` or `server`) and
  `GET /api/projects/:id/code-index?branch=` (`{ projectId, branch, files, tests, reach: [{ file, tests, origin }],
  builtAt, truncated }`); and `impact.unreachedFiles` in the impact resolution.
- **The editor service protocol** (`packages/editor/src/protocol.ts`): the requests `piwi/fileSummary`,
  `piwi/testsForFile`, `piwi/runArgs`, `piwi/status`, `piwi/runStatus`, `piwi/failures`, `piwi/trace`, `piwi/mcp`,
  `piwi/renderSteps`, `piwi/selections`, `piwi/runSelection` and `piwi/refresh`,
  the notifications `piwi/setCredentials` (client to server) and `piwi/runStatusChanged` (server to client), the
  client commands the service names (`piwi.openInDashboard`, `piwi.runTests`, `piwi.openTrace`, `piwi.runCommand`,
  `piwi.copyText`) and the diagnostic
  codes `brittle`, `watch`, `locator-break`, `ci-failure` and `timeout`. A published client talks to the service it bundles, so
  this freezes at the client release that ships it rather than with the instance.
- **`GET /api/projects/:id/branch-failures?branch=`** (`{ run: { id, status, branch, startTime, totalTests,
  passedTests, failedTests, flakyTests, skippedTests } | null, failures: [{ executionId, testCaseId, title, file,
  line, status, headline, location, traces, screenshot, clusterId }] }`, at most 200 failures; `traces` and
  `screenshot` are stored paths under `/api/files/`), which the editor service polls.
- **The VS Code extension** `piwitests.piwi`: its command ids (`piwi.connect`, `piwi.refresh`, `piwi.runTestsForFile`,
  `piwi.openInDashboard`, `piwi.openRun`, `piwi.runSelection`, `piwi.copyMcpConfiguration`, `piwi.pairPicker`, and the
  service's commands above), the settings
  `piwi.serverUrl` and `piwi.project`, the secret `piwi.apiKey`, and the MCP provider id `piwi.mcp`. Keybindings and
  settings users write name them. It exports no API to other extensions.
- **The JetBrains plugin** `dev.piwitests.piwi`: its action ids (`Piwi.Connect`, `Piwi.Refresh`,
  `Piwi.RunTestsForFile`, `Piwi.RunSelection`, `Piwi.OpenInDashboard`, `Piwi.CopyMcpConfiguration`, `Piwi.PairPicker`),
  which keymaps name; the tool window
  `Piwi` and the status bar widget `piwi.status`; the project settings stored as `PiwiSettings` in `.idea/piwi.xml`
  (`serverUrl`, `project`); the password-safe entry for the key (service `Piwi`, user `apiKey`); and its floor,
  build 233 (2023.3). Raising the floor is a breaking change for users of older IDEs.
- **Send to editor** (`@piwitests/core/editor-send`): the pairing address `<endpoint URL>#<token>` (an http URL on the
  loopback interface with a port, a token of at least 16 URL-safe characters); the request, `POST` to the endpoint with
  `Authorization: Bearer <token>` and a JSON body `{ kind: 'locator', text }` (at most 4,000 characters) or
  `{ kind: 'steps', steps }` (a steps document, at most 2 MB); the answers 200 `{ inserted, file }`, 400, 401, 413 and
  422 `{ error }`. The endpoints: `/piwi/send` on the port VS Code chooses, `/api/piwi/send` on a JetBrains IDE's
  built-in server. The commands `piwi.pairPicker` (VS Code) and `Piwi.PairPicker` (JetBrains). A paired Piwi Picker
  and a newer editor must keep talking, so the body only gains optional fields.
- **`GET /api/projects/:id/locator-alternatives?file=`** (`{ items: [{ testCaseId, location, method, alternatives,
  lastSeenAt }] }`) and the **`file`** filter of `GET /api/projects/:id/test-cases`, which the editor service calls.
- **The cache file** `.piwi/locator-index.json`, keyed `<instance URL>|<project>|<branch>`: local state, not a contract,
  listed so it is not mistaken for one.

**Recommendation:** freeze each contract as it ships; new fields are optional additions. `confidence` and a site's
`action` are closed sets: a new value would be misread by a hook that branches on them.

## Settled (for reference)

Decided and shipped while the audit was fresh:

- **Query parsing (D10)** — a `requireIntQuery`/`optionalIntQuery`/`queryFlag` helper trio
  (`server/utils/query-params.ts`) gives every query-parsing route one **clamp-and-400** contract: present-but-invalid
  is a 400 (never a silent default, never a dropped filter), absent falls back to the declared default, integers clamp
  into `[min, max]`. Applied to the int params on `slow-tests`, `timeout-opportunities`, `flaky-tests`, `performance`,
  `ai-steps`, `spec-health`, `stability-trend`, `settings/ai/usage`, cluster `commits`, `projects/[id]` and `links`;
  the boolean flags on `performance` (`fullRunsOnly`), `quarantine` (`candidates`), execution `diagnosis-context`
  (`includeImages`) and the three diagnosis POSTs (`force`); and the `subscriptions` `projectId` filter that used to
  silently return everything on garbage input. The strictness ships before the freeze (flipping silent-default to 400
  is the breaking part, so it lands pre-1.0). Live-verified: garbage/float/bad-bool → 400, valid → 200, absent →
  default.
- **Error conventions (D8)** — the same failure class now answers with the same status across the surface.
  Uniqueness conflicts are **409** everywhere (projects, tags, users join test-functions, which already was); a
  missing notification channel is **404** everywhere (subscription create was 400, subscription patch was 403 — both
  now 404, matching channel test/delete). Validation failures stay **400** (present-but-invalid input, unchanged). The
  env-managed-conflict semantic is documented as one rule — *the environment is authoritative for the fields it owns* —
  expressed at the two natural granularities: `wasted-waits` owns the whole setting so a write is refused with **409**,
  while `settings/ai` owns only provider/key/baseUrl so those are ignored and model-only overrides still apply (both
  now say so in their OpenAPI). The soft-fail family — the three "test the destination" endpoints
  (`channels/[id]/test`, `settings/ai/test`, `settings/smtp/test`) that return **200 `{ success: false, error }`**
  when a reachable destination rejects the delivery — is documented in each route's OpenAPI `responses`,
  distinguishing the delivery outcome from request-level errors (which keep their 4xx/503).

  For the machine-readable code, the chosen mechanism is the **`data.errorCode` convention** (not a global error
  handler, which would have to reimplement Nuxt's whole error path). Every server route throws a new `apiError`
  helper (`server/utils/api-error.ts`) instead of `createError` — all 329 sites migrated — so the serialized `data`
  is **always** an object `{ errorCode, issues? }`, never the bare zod-issues array it used to be. `errorCode` is a
  stable string from a shared vocabulary (`shared/utils/error-codes.ts`): it defaults from the status (404 →
  `NOT_FOUND`, 409 → `CONFLICT`, a 400 carrying issues → `VALIDATION_ERROR`, …) and is overridden where a client
  needs to distinguish failures that share a status — the two "not configured" 503s become `AI_NOT_CONFIGURED` vs
  `SMTP_NOT_CONFIGURED`. The demo service worker emits the same shape from the same vocabulary. No consumer read the
  old nested `data`, so the shape change broke nothing; adding a code later is additive (unknown codes fall back to
  the status). Live-verified: dup → 409 `CONFLICT`, missing channel → 404 `NOT_FOUND`, invalid body → 400
  `VALIDATION_ERROR` + `issues`, other 400 → `BAD_REQUEST`.
- **Phantom shard fields (D3)** — run-level `shardIndex` was on the wire in every reporter body but nothing read it.
